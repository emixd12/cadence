### Location prompt on the owner's Mac (Ticket 165), October 24

Evidence comes from the unified log (`/usr/bin/log`; in zsh, `log` is a builtin).
Cadence's "location result" lines are info level, so only a live
`log stream --level info` keeps them. Coordinates were not recorded. No agent
answered a system dialog, and no TCC or Location Services setting changed.

- **First prompt: pass.** At 02:42:09 BST the orchestrator turned Travel estimates off
  and on by accessibility scripting. At 02:42:10 Cadence called
  `requestWhenInUseAuthorization` with status NotDetermined, and CoreLocationAgent
  showed the prompt ("handle auth-prompt from locationd"). At 02:42:12 it answered
  `response=1`, and the status became `AuthorizedAlways`, macOS's granted status for
  desktop apps. It has stayed granted on every later read. This is the first
  permission prompt observed on this Mac: September's Developer ID builds without the
  location entitlement timed out with no prompt. The signed entitlement is the
  likely fix. That read itself ended "inactive", because the adapter (`location.m`)
  stops whenever `NSApp.active` is false, and the system prompt held focus.
- **Foreground position: pass.** At 03:14:52 the owner, with Cadence frontmost,
  turned Travel estimates off and on. No dialog appeared. The screen showed "A
  current position is available. Cadence did not save it." and "Travel settings
  saved." The log shows locationd "Sending location to client" and "cadence location
  result available" 17 ms after the request.
- **The "timeout" line that followed is a second request, not a missed callback.**
  - The Travel panel calls `readLocation` three times. `locate()` reads with
    permission (request 1). The `refreshPermission()` calls in the `finally` blocks of
    `save()` and `locate()` read without it.
  - On desktop the permission check is not status-only: `readLocation(false)` runs the
    same native `foreground_location` command, which sends `requestLocation` once
    authorized.
  - The Rust command uses `try_lock`. The check from `save()` arrived while request 1
    held the lock, so it failed at once as "bridge" without a Core Location request.
  - The check from `locate()` started 2 ms after request 1 ended (request 2,
    03:14:52.892). locationd subscribed it but sent no location. CoreLocation's own
    10-second `onLocationRequestTimeout` fired at 03:15:02, and the adapter's
    12-second deadline logged "unavailable reason timeout" at 03:15:05.
  - The same pairs appear at 03:08:16/03:08:36 and 02:43:35/02:43:38: the first read
    receives locationd's recent fix at once, and a read seconds later waits for a new
    fix that does not arrive within 10 seconds on this Mac. Why fresh fixes are slow
    here is not established. Wi-Fi is on and is the active route.
- Effect: after a successful read, the timed-out check sets the panel's permission
  state to empty, so the "Device location: allowed." line disappears. Opening
  Settings › Travel while authorized also triggers a real location request. Neither
  blocks Ticket 165's prompt, grant or position checks. A status-only native
  permission query would remove both; that is follow-up work, not part of 0.1.5.
- Launch Services is not the cause. locationd's "not a plugin or an app" (`-10814`)
  lookups and visit-monitoring subscriptions also appear for Apple's Reminders and
  Shortcuts; they are routine. Launch Services resolves `app.cadence.desktop` to
  `/Applications/Cadence.app`, and the running app is registered correctly. The agent
  unregistered three records whose paths no longer existed and re-registered the
  installed app; the retry above followed that cleanup.
- Still open for Ticket 165: the denied state (turn Cadence off in Location Services
  and check "Device location: blocked."), and the never-authorized macOS user test
  with the 0.1.5 DMG.

## Why 0.1.5

On October 23, PR #111 (read-only Outlook, iCloud and Hevy connectors) and PR #112
(Ticket 215, Behavior Where) reached main, and their hosted migrations were applied.
The hosted Behavior writer now requires `where_kind` in every desktop upsert.
Published 0.1.3 (SQLite schema 17) does not send it, so its Behavior sync fails
closed with "Update Cadence". Local data stays on the Mac.

0.1.5 restores Behavior sync. It is newer than every published version (0.1.3).
Version 0.1.4 was never built or published; its session fix ships here.

Desktop changes since the 0.1.3 source `dcefe7e`:

- PR #115: the 0.1.4 linked-session callback fix.
- PR #111: Outlook Calendar, iCloud Calendar and Hevy panels, their disposable
  caches in `calendar-cache.sqlite3`, and Timeline context.
- PR #112: SQLite migration `0018_behavior_where.sql` (schema 18) and the Where
  sync contract. Existing location text becomes Where = A place.
- PR #134: the Hardened Runtime location entitlement
  `com.apple.security.personal-information.location` (Ticket 165).
- Dependency updates, including `rustls` 0.23.46.

The travel release train (PR #138, desktop schema 19–20) names 0.1.5 as its minimum
desktop version. It will move to 0.1.6; this packet does not edit #138.

## Connector gating

Determined October 23 from main `f922685` and the production deployment.

The desktop has no client-side connector flag. A production build with a broker
origin renders Outlook Calendar, iCloud Calendar and Hevy in Settings → Connected sources
for a linked account. The hosted broker at `https://app.cadence-me.com` decides the
state of each one.

Production has none of the connector secrets. `vercel env ls production` lists no
`CONNECTOR_CREDENTIAL_*` and no `OUTLOOK_CALENDAR_*` names (names only; no values
were read). The connector routes exist: unauthenticated requests to
`/api/{hevy,outlook-calendar,icloud-calendar}/connection` return 401, and an
unknown path returns 404. Without the keyring, `getConnectorConnection` reports
`not_configured` for all three. Outlook also reports it without its OAuth settings.

What a 0.1.5 user sees:

| Mode | Settings → Connected sources | Timeline | Daily Brief settings |
|---|---|---|---|
| Local (no account) | Each panel: "Link a Cadence account on this Mac to connect …" | Nothing from the three sources | Unchanged |
| Linked account | Each panel: "… connection is not configured." and "… not configured for this Cadence deployment." No key, password or connect controls | Nothing; `not_configured` is not an active Timeline state | The three disclosures stay hidden; they appear only for a connected source or one already turned on |

The web app at app.cadence-me.com shows the same linked-account state today.
Conclusion: no unaccepted connector is usable, and none is broken. The panels are
visible but say plainly that the connection is not configured.

Enablement is server-side only. Setting the `CONNECTOR_CREDENTIAL_*` keyring in
production would at once enable Hevy and iCloud on web and on every installed 0.1.5
or later desktop. Outlook also needs the `OUTLOOK_CALENDAR_*` settings. Installed
desktop connector checks (Keychain, `cadence://` deep links, per-source cache
cleanup) remain unverified, so enable these only after their own acceptance.

## Rollback

Nothing is published, so no public rollback applies. Installed copies of 0.1.2 and
0.1.3 keep failing Behavior sync until 0.1.5 or later ships; local data stays safe.

On a Mac where 0.1.5 was installed, prefer fixing forward. An older app refuses the
migrated database with "The local database needs a newer Cadence version", so a
rollback restores the app and the protected database together. Changes made under
0.1.5 that synced stay hosted. Unsynced ones survive only in the set-aside copy.
With Cadence quit, and `B` set to the backup folder:

```bash
D="$HOME/Library/Application Support/app.cadence.desktop"
mkdir "$B/set-aside-0.1.5"
for f in cadence.sqlite3 cadence.sqlite3-wal cadence.sqlite3-shm; do [ -e "$D/$f" ] && mv "$D/$f" "$B/set-aside-0.1.5/"; done
cp -p "$B/before.sqlite3" "$D/cadence.sqlite3"
mv /Applications/Cadence.app "$B/set-aside-0.1.5/"
ditto -x -k "$B"/Cadence-*.zip /Applications
```

The restored 0.1.2 or 0.1.3 still cannot sync Behaviors against the hosted Where
schema. Do not reverse the hosted backfill to make it write
([rollout plan](2026-10-21-behavior-where-rollout.md#failure-handling)).
