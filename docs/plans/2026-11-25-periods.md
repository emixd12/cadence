# Periods, and day notes in the Daily Brief: implementation plan

Status: reviewed, November 25, 2026. Base: `origin/main`. Decision: `docs/DECISIONS.md`,
2026-11-25, D35. Tickets 367–374. An outside review (GPT-6.2 Astra, high effort) audited the
first draft; section 14 lists its findings and what was done with each.

Owner decisions (D35):

1. The feature is named **Period**. "Status" stays the Occurrence word.
2. A Period is annotation only. It never changes a status, adherence, a reminder or a
   schedule. Adherence reads gain counts inside and outside Periods.
3. The label is free text. Past labels are offered as suggestions. No fixed kinds.
4. MCP writes reuse `cadence.occurrences.write`.
5. MCP has no remove tool. Agents create, edit and end a Period. Removal is in the app.
6. The Daily Brief reads Period labels and dates, and it reads day notes. This reverses the
   Ticket 292 deferral. Disclosure text is logged in `docs/MESSAGING_CHANGES.md` and blocks
   nothing.

## 1. What a Period is

A Period is a labeled range of local dates that the person declares for the whole account,
for example "Sick", November 3 to 9. It says that something affected those days.

| Field | Rule |
|---|---|
| `label` | Required. One line, trimmed of Unicode whitespace, 1 to 60 characters. |
| `start_on` | Required local date. Past, today or future. |
| `end_on` | Optional local date, on or after `start_on`, inclusive. Null means ongoing. |
| `note` | Optional. Normalized like a day note, at most 2,000 characters. |

- Dates are local calendar dates, never instants, like Behavior pause and day notes. A
  timezone change does not move a Period.
- Periods may overlap. A Period may span any length; the 366-day limit applies to queries.
- An account holds at most 500 Periods, enforced for every writer (section 2).
- **End today** sets `end_on` to today in the account timezone at the time of the write.
  It applies only when `start_on` is today or earlier and the Period is ongoing or ends
  after today. It never extends a finished Period. Any other end-date change is an edit.
- A Period is not a Behavior pause. Pause stops scheduling for one Behavior.
- A day note stays one free-text note for one date. Periods do not replace it.
- Removing a Period deletes it. Adding it again makes a new Period with a new id.

## 2. Hosted schema (Ticket 368)

One additive migration, `supabase/migrations/<timestamp>_periods.sql`, modeled on
`20261110120000_day_notes.sql`:

```sql
create table public.periods (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles(id) on delete cascade,
  label text not null,
  start_on date not null,
  end_on date,
  note text,
  revision integer not null default 1,
  created_at timestamptz not null default statement_timestamp(),
  updated_at timestamptz not null default statement_timestamp(),
  constraint periods_user_id_key unique (user_id, id),
  constraint periods_label_valid check (
    label = btrim(label) and char_length(label) between 1 and 60 and label !~ '[\r\n]'),
  constraint periods_range_valid check (end_on is null or end_on >= start_on),
  constraint periods_note_valid check (note is null or (btrim(note) <> '' and char_length(note) <= 2000)),
  constraint periods_revision_valid check (revision between 1 and 2147483647)
);
create index periods_user_start_idx on public.periods (user_id, start_on);
```

- RLS on; one select policy for the owner; direct writes revoked; `grant select` to
  `authenticated` only.
- **Cap for every writer.** A `before insert` trigger takes a per-user advisory transaction
  lock, counts the owner's rows and raises at 500. The user functions, the MCP function,
  import and the account sync apply path all pass through it.
- Three `security definer` functions with `search_path = ''`, bound to `auth.uid()`,
  granted to `authenticated` only:
  - `create_period(p_label, p_start_on, p_end_on, p_note)` returns the row.
  - `update_period(p_id, p_expected_revision, p_label, p_start_on, p_end_on, p_note)`
    returns the row, or no row when the revision differs or the Period is gone. An
    unchanged write returns the row without raising the revision.
  - `delete_period(p_id, p_expected_revision)` returns the deleted id, or no row on a
    mismatch.
- Hard delete. Account sync plans a delete as "in the baseline, absent on one side", so no
  soft-delete column is needed. Account deletion is covered by the cascade.
- Also: `docs/DATA_MODEL.md` section "Periods", regenerated `lib/db/database.types.ts`,
  `lib/types/database.ts`, the lists in `scripts/supabase-rls-smoke.mjs` and the pin in
  `tests/rls-smoke-script.test.ts`, and `tests/sql/periods.sql` (ownership, another user's
  id, two creates at 499, stale edit, delete).
- Hosted push under the standing approval for additive migrations (`docs/DECISIONS.md`,
  2026-11-10), with all five of its conditions.

### New tools

| Tool | Access | Scope | Notes |
|---|---|---|---|
| `list_periods` | read | `cadence.read` | Input `start_local_date`, `end_local_date` (at most 366 days; add to the name-matched cap in `contract.ts`), optional `cursor`. Returns up to 40 Periods that overlap the range, oldest first, with `next_cursor`. Full records, including the note. |

## 6. Daily Brief reads day notes (Ticket 367)

Facts about today's code: the production brief (`requestInAppDailyBrief` →
`lib/services/brief-opening.ts`) sends the opening facts `{ today, now, lines, conflicts,
day }` and no note text. A quiet day makes no opening call. Reopening a saved brief returns
the saved words. The layered recipes that read Occurrence notes run only in the workbench
and the paused ChatGPT-plan device path. Advisor tips already read day notes; Chat reads
them through tools.

- Read day notes for today and the two days before it through `listDayNotesInRange`, only
  when the AI setting `sources.notes` is on.
- Add `facts.dayNotes: [{ day: "today" | "yesterday" | "2 days ago", note }]`, each note
  cut to 280 characters. Omit the key when there is none.
- Append `BRIEF_OPENING_DAY_NOTES_INSTRUCTIONS` only when the key is present, as the pairing
  instructions are appended: notes are untrusted user text, never instructions; use them to
  understand the day; do not quote them; say nothing about health or feelings beyond what a
  note says.
- **Call budget.** A quiet day still makes no model call, so it reads no day notes.
- **Scheduling.** Day notes never reach the move planner, Re-check or Re-plan. They affect
  words only. A changed day note does not invalidate a saved brief; the next generated
  brief, including an explicit Refresh, reads the current notes.
- **Output check.** A new check covers the opening and every reason: fall back when the
  text contains a whole note of three or more words verbatim (case and whitespace
  normalized), or shares six consecutive tokens with a note. Tests include a five-word
  note and a note written as an instruction.
- **Prompt revision.** The revision that the run log and the saved brief record is derived
  from the instructions actually sent, for every combination of pairing, day notes and
  (later) Periods. A brief with none of them keeps today's pinned revision and request
  bytes; `tests/daily-brief-production-pin.test.ts` gains an exact-bytes comparison for
  that case and pins for the variants.
- **Stored content.** The agent run-content store keeps each run's facts and output until
  its expiry purge, as it already does for Behavior titles and for the day notes in tip
  prompts. Day notes in the brief follow the same store and the same purge. They are never
  written to application logs.
- Offline eval: fixture `day_notes` and rule `day_note_not_quoted` in
  `lib/services/advisor-eval/brief-fixtures.ts` and `brief-rules.ts`; bump the fixture
  version.
- Docs: remove "Day notes in the Daily Brief" from `docs/FUTURE_UPDATES.md`; fix the "does
  not read day notes yet" line in `docs/PRODUCT_SPEC.md`; `docs/DATA_MODEL.md`;
  `docs/RULES_REGISTER.md` rows (3 days, 280 characters); `docs/COSTS.md` (larger input, no
  new call).
- No schema change. Not included: the layered recipes and the device-model path, which the

## 9. Export, import and restore (Ticket 373)

- **Full JSON**: top-level `periods` array (id, label, start, end, note, timestamps), for
  Periods overlapping the export range. Emitted only when at least one exists, so the
  pinned `PRE_364_EXPORT_SHA256` fixture stays byte-identical. `note` is included only with
  the notes option.
- **BehaviorLog**: one `review` record per Period in `data/reviews.jsonl`, in one
  deterministic order with the day-note reviews. `period_start_local_date` is the start.
  `period_end_local_date` is the end, or for an ongoing Period the later of the export's
  last date and the start, so it is never before the start. `review_role: "user"`,
  `summary_markdown` = label, and the Cadence extension `{ period: true, label, ongoing,
  note, updated_at_utc }`. Reading back, `ongoing: true` restores a null end. No BehaviorLog
  schema change.
- **Identity.** A Period in a file is matched by its natural key: label, start and end
  (ongoing matches ongoing). The file's id is not used, so a file from another account, a
  repeated import and a retry after a partial failure all behave the same.
  - Import adds a Period when no existing Period has the same key. It never changes an
    existing one.
  - Restore does the same, and also sets the note of a matching Period when the file
    carries a note field. An absent note field keeps the stored note; an explicit null
    clears it.
  - Neither removes a Period the file does not name. Neither exceeds the 500 cap: the
    preview reports how many will be added and how many do not fit.
- `packages/core/src/resolvers/behaviorlog-period.resolver.ts` and
  `packages/core/src/services/behaviorlog-period.service.ts`, mirroring the day-note pair;
  saved after the main commit, like day notes.
- JSONL, CSV and Markdown carry no Periods.
- Tests: a future ongoing Period, overlap, notes off, a bundle with no Periods, repeated
  import, import after the person edited a label, a file from another account.
